# Изолированное исследование рендера

Исходная точка: `415a6552eb0cc3d9cdff4a59d164b98f98049a47`, Mindustry v160.7, Arc 7445105cd2683daf5b9ac7033ebb07265d3e814d. Итог и ограничения — в [отчёте](../../docs/OPTIMIZATION_RESEARCH.md).

Эти Java-файлы **не подключены к исходникам или сборке рабочего мода**. [prepare.py](prepare.py) распаковывает `git archive` указанного коммита в игнорируемый каталог `.gradle/optimization-research-415a655/snapshot`, генерирует там копию адаптера и инструментирует только эту копию. Запускаемый JAR и игровые данные создаются внутри snapshot. Исходный BuildWheel только копируется. Пользовательские сохранения и настройки не читаются и не меняются.

В snapshot у эталонного UnitProjection убран `final`, чтобы сравниваемый адаптер можно было поставить в тот же HUD. Тело эталонного рендера сохранено. Это исходный контроль, а не утверждение о тождестве машинного кода/JIT исходному JAR. В обёртке HUD есть условные измерительные ветви. Счётчики через GL proxy включаются только в диагностических проходах; временные измерения идут без proxy.

## Воспроизведение

Требуются Python 3, полный JDK 17, установленный desktop.jar Mindustry v160.7 и уже доступные зависимости Gradle. Пути ниже соответствуют исследованной машине. В PowerShell из корня репозитория:

```powershell
python research/optimization-415a655/prepare.py
$env:ORG_GRADLE_PROJECT_mindustryDesktopJar='C:/Program Files (x86)/Steam/steamapps/common/Mindustry/jre/desktop.jar'
$env:ORG_GRADLE_PROJECT_mindustryJava='C:/Program Files/Eclipse Adoptium/jdk-17.0.15.6-hotspot/bin/java.exe'
$env:ORG_GRADLE_PROJECT_buildWheelDirectory='C:/Program Files (x86)/Steam/steamapps/common/Mindustry/saves/mods/BuildWheel'
$env:ORG_GRADLE_PROJECT_researchReports="$PWD/research/optimization-415a655/repeat-new"
./gradlew.bat -p .gradle/optimization-research-415a655/snapshot optimizationResearch --offline
```

Для повторения только исправленных фаз игрового кадра добавьте `-PresearchFrameOnly=true` и задайте новый каталог результатов. Перед повторной подготовкой дождитесь завершения предыдущей сборки/клиента. Нужен настоящий графический сеанс Windows/SDL; это не headless GL и не эмуляция других ОС. На неподдерживающем GPU shader-кандидаты могут отсутствовать; текущий измеритель рассчитан на исследованную desktop-конфигурацию, переносимые production-fallback в нём намеренно не завершены.

Для отдельной проверки максимальных drift/углов и custom blend добавьте `-PresearchProofOnly=true`, без frameOnly. В drift-proof исходные состояния адаптера устанавливаются в точные предельные значения через test-only reflection; это проверка устойчивого крайнего состояния, не симуляция переходного движения.

Проверка исходного рабочего кода, без исследовательских патчей:

```powershell
./gradlew.bat build benchmark projectionBenchmark smoke --offline --rerun-tasks
```

Это использует те же три свойства окружения desktop/Java/BuildWheel. Полный JDK нужен исследователю для `ThreadMXBean`; встроенный Java runtime игры может не содержать модуль management.

```powershell
python research/optimization-415a655/summarize.py
```

создаёт [MEASUREMENTS.md](MEASUREMENTS.md) и [summary.json](summary.json). Квантили — внутри каждого блока; диапазоны медиан блоков не называются общей медианой или доверительным интервалом.

## Состав и ограничения прототипов

- [ResearchBatch.java](ResearchBatch.java): обычный SpriteBatch со счётчиками, no-GL, VBO, PMA, раздельный RGB/alpha, dual-source и coherent framebuffer fetch; scoped замена батча только вокруг HUD.
- [ResearchQueue.java](ResearchQueue.java): захват готовых вершин, последовательный replay и чередование готовых texture/blend-серий разных групп. Порядок каждой группы сохранён; общий guard проверяет AABB всех квадов. Полный граф панелей/надписей HUD здесь **не реализован**.
- [OptimizationResearch.java](OptimizationResearch.java): одинаковые состояния настоящих типов, A–B–B–A, четырёхсторонние комбинации, FBO-сверки RGBA, LOD, кеш, несколько окон и отдельные фазы клиента.
- [ResearchLauncher.java](ResearchLauncher.java): скрытый SDL-клиент с отдельным каталогом данных.

Флаги генерируемого ResearchProjection: `1` — пропуск прозрачных/вырожденных частей; `2` — вынесение одинаковой цветовой интерполяции зеркальных сторон; `4` — повторное использование последней подготовки Unit только внутри одного пакета. Флаг `1` исследован на штатных normal/additive: **не является готовой универсальной фильтрацией произвольного Blending**. Контрпример ONE/ONE сохранён отдельно. Unified поддерживает только normal/additive; исключение на другом blend не заменяет полноценный production-fallback.

## Реестр прогонов

| Каталог | Использование |
| --- | --- |
| run-1 | Прерванный ранний измеритель; результатов для выводов нет. |
| run-2 | Предварительные счётчики и пиксели. CPU повторял неочищаемый FBO; фазы кадра ошибочно имели пустые группы из-за paused team stats. **Числа кадра не использовать.** |
| run-3 | Исправлены очистка, team stats и проверка непустого HUD; добавлены GPU-таймеры, fetch, кеш и восстановление состояния. HUD-таймер ещё не включал вход в scoped backend. |
| run-4 | Включён вход в HUD-таймер; добавлены явная комбинация skip/dual, no-GL кандидаты, queue и LOD. |
| run-5 | Повтор, прямой/обратный порядок queue; три синтетические страницы текстур, последовательности blend-run, расширенная проверка GL/Unit. Основная пиксельная матрица и изолированные сравнения. |
| run-6, run-7 | Исправленные фазы кадра: штатный commandMode всегда включён; mode 0 отключает **только draw HUD**, модель продолжает обновляться. Начальная сцена дополнительно прогрета; параметры HUD заданы явно. Есть фиксация представителей/размеров и контрпример custom blend. |
| run-8 | 96 RGBA-сравнений предельного drift: 3 типа × 2 угла × 1/11 проекций × P=64/150 × alpha 1/0,32 × 2 кандидата. Отдельный контрпример alpha=0 при ONE/ONE. |
| baseline-validation | Свежие build/test/benchmark/projectionBenchmark/smoke рабочего коммита без прототипов. |

Фазы mode 0 в run-3/4/5 меняли также штатный commandMode: их нельзя использовать как чистую цену отключения HUD. Сравнения режимов 1–4 сохраняли commandMode, но последовательные фазы и сильный системный разброс всё равно ограничивают выводы. Для итогового сравнения кадра используются run-6/7.

## Значения CSV

- `times.csv`: p50/p95/p99/min/max CPU draw+flush; `completed` — время всего блока с заключительным glFinish, делённое на пакеты. Это разные метрики. Очистка FBO включена в CPU GL-пакеты, но не в GPU query.
- `gpu-timers.csv`: настоящий `TIME_ELAPSED`, 64 асинхронных query на вариант, результаты читаются после готовности вне интервала. Это GPU timeline, включая возможные простои подачи команд; не эксклюзивный GPU busy. Core.gl30 оставлен null: локальный SdlGL30 используется лишь для query. Unsigned 32-bit чтение, насыщение отклоняется; измеренные интервалы намного меньше 4,29 с.
- `counts.csv`, `conquer-profile.csv`: отдельные диагностические проходы; empty flush не равен draw. `-1` — значение не собиралось данным батчем. `N`/`A` — normal/additive и длина непустой серии. Zero explicit buffer upload у VertexArray **не означает отсутствия передачи данных драйвером**.
- `parity.csv`: сравнение всего RGBA8 FBO с неизменённым адаптером. `changed-pixels` — число отличающихся пикселей; `max-rgb` и `max-alpha` — наибольшее отклонение канала 0–255. Среднее по всему FBO не заменяет локальную максимальную ошибку.
- `queue.csv`: только 11 изолированных проекций, P — параметр размера по hitSize, а не сторона всего изображения. Захват/границы/replay входят во время. P=150 вызывает пересечения и возврат к serial.
- `frames.csv`: 120 кадров после 50 прогревочных в каждой прямой/обратной фазе; elapsed внутри DesktopLauncher.update, без SDL swap/presentation. Счётчики превышений 8,33/16,67 мс — превышения CPU-интервала, **не измеренные пропуски показанных кадров**.
- `frame-fixture.csv`: контроль числа групп, уникальных представителей, их типа и фактического P в исправленных фазах.
- `textures.csv`: синтетические страницы (замена texture-ссылок двух регионов на отдельные 1×1 текстуры с восстановлением в finally), не настоящий установленный модовый UnitType.

Пиксельная projection-матрица: 5 типов × 8 состояний × 2 alpha × 3 фона = 240 сравнений **на кандидат**. HUD: 48 конфигураций × 3 окна × 4 кандидата = 576 сравнений за полный прогон. 48 конфигураций — выбранное сочетание факторов, не полный декартов перебор. Редактор представлен прозрачностью его HUD и геометрией; целая панель редактора этим FBO-тестом не заменяется. Её ввод/визуал проверяет исходный smoke.

Один и тот же Unit в 11 изолированных позициях — нагрузочная верхняя граница reuse. В реальном HUD один Unit может повторяться максимум в десяти сохранённых группах, поскольку нераспределённая группа его исключает. Частота этого случая в реальной игре неизвестна.

В run-5 измерители уже соответствуют описанным CPU/pixel-экспериментам. В последней версии шаблонов после него добавлены исправленный frame-only контроль, proof-only и дополнительный drift-proof в полном запуске; это не меняет прежние сырые CSV. Перечень файлов и SHA-256 приведён в [manifest.json](manifest.json).

Время CPU шумное; частоты, температура, внешние процессы, paging и энергия не контролировались. Пиксели и счётчики гораздо устойчивее. Эти результаты не доказывают рост FPS, уменьшение энергии или универсальную выгоду другого GPU/ОС. Коммиты и push для исследования не выполнялись.
